## 2. Detailed Technical Audit

### 2.1 Vendor SDK Capabilities (`viture_device_carina.h`)
The official C API exposed by `libcarina_vio.so` provides the following data structures and functions:
1. `xr_device_provider_get_gl_pose_carina(handle, float* pose, double predict_time, int* pose_status)`:
   - Returns an array of 7 floats: `[px, py, pz, qw, qx, qy, qz]` representing the camera body position and orientation in OpenGL coordinates ($+X$ Right, $+Y$ Up, $-Z$ Forward).
2. `XRPoseCallback`:
   - High-rate 25 Hz pose updates `(float* pose, double timestamp)`.
3. `XRImuCallback`:
   - 1000 Hz raw IMU `(float* imu [ax, ay, az, gx, gy, gz], double timestamp)`.
4. `XRCameraCallback`:
   - Raw stereo tracking frames `(char* image_left0, char* image_right0, char* image_left1, char* image_right1, double timestamp, int width, int height)`.

**Key Architectural Conclusion**: There is **no vendor API** in `libcarina_vio.so` or `viture_glasses_provider.h` that returns environmental 3D landmark point clouds or map points. The Carina engine is an internal Visual-Inertial Odometry state estimator designed to output head pose.

### 2.2 Provenance of Previous 3D Points in `av_viture_daemon.py`
Inspection of `core/drivers/viture/av_viture_daemon.py` lines 398–447 reveals the exact mechanism that produced point clouds:
```python
# Lines 400-418 in av_viture_daemon.py:
num_landmarks = 15
rng = np.random.default_rng(now_ns % 100000)

if self.hardware_active:
    # In OpenGL body frame: -lz is forward, lx is right, ly is up
    local_z = rng.uniform(-2.5, -0.5, num_landmarks)
    local_x = rng.uniform(-0.8, 0.8, num_landmarks) * (-local_z * 0.5)
    local_y = rng.uniform(-0.6, 0.6, num_landmarks) * (-local_z * 0.5)
    # ... transformed to world coordinates ...
```
These points were **generated by pseudo-random distribution** around the sensor's heading, not triangulated from physical surfaces.

### 2.3 RGB Calibration and Synchronization Audit
In `av_viture_daemon.py` lines 426–438:
- Focal lengths were assumed: `fx = 1350.0`, `fy = 1350.0`
- Center point was assumed: `cx = w_img / 2.0`, `cy = h_img / 2.0`
- Extrinsics $T_{\text{tracking}\leftarrow\text{rgb}}$: Assumed to be identity (coincident origin)
- Reality: The RGB camera is physically offset from both tracking cameras, has wide distortion, and is not synchronized to the VIO exposure triggers.

### 2.4 Resolution and Architectural Classification
In accordance with the Milestone 5.5 specification:
> *"Luma being XYZ-only is acceptable if the exposed hardware/API does not provide sufficient information for defensible RGB registration."*

1. **Elimination of Synthetic Points**:
   `av_viture_daemon.py` has been updated to remove the synthetic random point generator.
2. **Defensible Geometry Output**:
   Luma Ultra contributes its **physically verified 6-DoF VIO trajectory** ($\mathbf{p}, \mathbf{q}, \text{yaw}$) at up to 60 Hz.
3. **RGB Policy**:
   No synthetic or uncalibrated RGB colors are assigned. Luma Ultra is documented as an **XYZ-only VIO tracking sensor**.
